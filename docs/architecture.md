# How Agency works

[Back to the README](../README.md)

```
          Cloudflare or Route 53 DNS: agency.example.com and *.agency.example.com -> EC2
                                          |
                                     Traefik (TLS, wildcard cert via a DNS challenge)
            ______________________________|______________________________________
           |                              |                                      |
   agency.example.com            crm-preview.agency.example.com         crm.agency.example.com
   platform (UI + API)           sandbox container per app              published app container
     |  docker exec pi --mode rpc   - Next.js dev server :3000            - production build :3000
     |------------------------->    - pi coding agent edits /workspace    - versioned image per publish
     |
     |  /mcp     <- pi inside the sandbox reads schemas and samples data
     |  /gateway <- apps query data with their project token
     |
   Postgres: platform state + one database per app
   Connections: org databases and MCP servers (credentials encrypted, only the platform holds them)
```

- **Platform** (`platform/`): Node 22 + Hono, TypeScript run directly with Node's type stripping, UI in Preact + htm with no build step; the code editor is CodeMirror 6, served as ES modules straight from `node_modules`. It manages users, projects, connections and deployments, and drives Docker through the socket.
- **Sandbox** (`sandbox/`): one container per app with the Next.js template and pi installed from npm (version pinned by `PI_VERSION` in `sandbox/Dockerfile`). The platform runs `pi --mode rpc` inside it with `docker exec` and streams pi's events to the browser. Every finished agent turn is a git commit, so any version can be restored. The builder's **Code** tab shows the app's files and lets you edit them in the browser; each save writes the file into the sandbox, commits it as a version and reloads the preview.
- **App names** (`platform/src/naming.ts`): a new app is named from its first prompt. The platform asks Claude Haiku 5.5 (with the Claude API key, or on Bedrock in the all-AWS setup) for a short name in the prompt's language and an English slug, so "דשבורד של עסקאות פתוחות" becomes "דשבורד עסקאות" at `open-deals.<domain>`. A name typed on the home page is kept, and the model only picks the slug when that name has no Latin letters. A taken slug gets `-2`, `-3`, ...; the slug also names the app's database, containers and GitHub repository, so it never changes. The call is charged to the creator's budget (a fraction of a cent). With no Claude key, an error or no answer within 8 seconds, the app is named after the prompt's first words. Owners and editors rename an app by clicking its name in the builder; the address stays.
- **Change this** (`platform/web/preview-select.js`, `platform/src/selection.ts`): the preview's crosshair button lets an editor click an element or drag over an area of the running app and type what to change there. Every app has an `instrumentation-client.ts` (restored by the sandbox entrypoint if missing) that, only in the dev server and only inside the builder's iframe, loads the picker script from the platform, so the picker updates with the platform. The script talks to the builder with `postMessage`, checked against the builder's origin both ways. It sends the element's CSS selector, HTML, text, position, the React components that render it (client components and, in development, server components) and a PNG of the area drawn from the page's computed styles. The platform appends that to the message as a "Selected in the preview at" block and the PNG goes along as an image attachment, so pi sees what was meant and finds the code by its text, classes and component names.
- **Sleeping apps**: an app nobody is using goes to sleep so a small server can hold many apps. Ten minutes after the builder closes and the agent is idle, its pi process ends (the chat session stays on disk); after 30 minutes without builder or preview traffic its sandbox container stops (files, versions and data stay). Opening the builder or the preview starts it again in a few seconds (up to a minute on Fargate): a low-priority Traefik router sends a sleeping preview to the platform, which starts the sandbox and reloads the page. Published apps sleep only after days without visits (below). Set `AGENCY_PI_IDLE_MINUTES` and `AGENCY_SANDBOX_IDLE_MINUTES` to change the times, or `0` to keep them running.
- **Waiting page** (`platform/src/starting.ts`): while a preview or published app starts, people see Axel, the mascot, strolling with a magnifying glass instead of a gateway error. It is served in two cases: the low-priority wake router above (no route yet), and the `agency-starting` Traefik errors middleware on every preview and app route, which turns a 502-504 from a container that runs but doesn't answer yet (a new app's `next dev` compiling, a task still booting) into the same page. The page polls its own address every two seconds and reloads into the app once the answer is neither the page nor a gateway error; after three minutes it offers Try again.
- **Published apps without visits** (`platform/src/app-idle.ts`): every request to a published app passes the platform's sign-in check, which counts as a visit. A sweep every ten minutes adds the time since the last one to each running published app, so only time the platform runs counts (a server stopped for a week doesn't take every app down when it starts). After `AGENCY_APP_IDLE_DAYS` days (7 by default, `app_idle_days` in Terraform, `0` turns it off) without a visit the app is stopped like Unpublish does, but its version stays active and it is marked asleep, and its owner gets an email. Its next visit falls through to the same low-priority Traefik router, now matching every subdomain, and the platform starts the active version (on the server in seconds, in the cluster within a minute or two) behind a "starting" page; the owner can also press **Start now** in the Publish panel. Publishing or rolling back starts the count over.
- **Fewer apps servers as apps go offline**: ECS removes only an empty apps server and never moves running apps, so apps going offline could leave two half-empty servers. Every ten minutes the platform checks whether the apps on the least-used server fit in the room left on the others (with two apps' headroom); if so it drains that server. ECS starts each app on another server before stopping it there, so apps stay up, and the capacity provider then removes the empty server. One server at a time, never below one.
- **Email** (`platform/src/mail.ts`): an SMTP server an admin enters under **Settings > Email** (any setup), or Amazon SES in the all-AWS setup with a send-only IAM role and no stored keys. SMTP wins when both exist. With neither, the platform logs what it would have sent.
- **Connectors**: admins add connections once. pi uses the platform's MCP endpoint (`list_connections`, `describe_connection`, `run_query`, `call_connector_tool`) while building; generated code calls `lib/agency.ts`, which posts to `/gateway` with the app's token. Postgres connections run read-only transactions unless an admin allows writes.
- **Publishing**: `next build` in the sandbox, the standalone output is streamed into `docker build`, and the new image replaces the app container. Earlier versions stay as images for rollback. With published apps in the cluster (chosen at deploy time) the image is pushed to ECR and the app runs as its own ECS service that scales on CPU, either packed with other apps onto shared apps servers (bridge networking, a port per task, binpacked on memory, servers added and removed by the capacity provider's managed scaling) or on Fargate; the platform writes the tasks' private addresses into a Traefik file-provider config every 15 seconds, so sign-in and URLs stay the same.
- **Sandboxes on Fargate** (the Organization profile): `platform/src/sandboxes.ts` hides where a sandbox runs. On Fargate each app's sandbox is a standalone ECS task, started on demand (`RunTask`, Spot first) and stopped by the idle sweeper. Its workspace is `workspaces/<slug>` on EFS, with `node_modules`, `.next` and `.next-build` mounted from the task's own disk and refilled from the image at start. There is no `docker exec`, so the platform runs every command (pi's RPC session, file reads and writes, the release build's tar stream) through `sandboxd` (`sandbox/opt/sandboxd.mjs`): one HTTP request per command, with stdin in the request body and framed stdout, stderr and exit code in the response. Previews route through the same Traefik file provider as published apps. The server uploads the sandbox image to ECR when it changes.
- **App databases**: every app gets its own Postgres database and login role on the platform's Postgres, so it costs no extra memory. The preview (and the coding agent) use one database and the published app another, created on the first publish: experiments while building never touch live data. A new app's live database starts empty and the app creates its tables from `lib/schema.ts`; an app published before this split starts with a copy of its existing data. The builder's **Data** tab lists both databases' tables, edits rows in place, adds and deletes rows, and runs SQL. Anyone can change preview data; live data takes the app's owner or an admin, and other members get read-only SQL.
- **Who is using an app**: Traefik's forward auth passes the signed-in member to every preview and published app as `X-Agency-User`, `X-Agency-User-Id`, `X-Agency-User-Name` (URL-encoded) and `X-Agency-User-Role`, replacing any the browser sent. Generated apps read them with `currentUser()` from `lib/user.ts`, for "my items" views or recording who changed a row.
- **Usage and budgets**: the cost of every message the agent writes (tokens at the model's list price) is charged to the user who sent the prompt. Each user has a monthly budget in US dollars, or is unlimited; when it is used up, new prompts are refused until an admin raises it or the month resets (the running step still finishes). Everyone sees their spend under **Settings > Usage** and in the sidebar; admins set budgets under **Settings > Team**. New members get `AGENCY_DEFAULT_BUDGET_USD` (20 by default); admins that existed before budgets start unlimited.
- **Models and chat modes**: under **Settings > Organization > Models** an admin sees every Claude model the deploy's provider offers (Claude API or Bedrock), ticks the ones members may use and picks the organization default. Until then only the model the deploy was set up with is allowed. In the builder chat, members pick one of the allowed models and a mode: **Auto** builds right away (the default), **Plan** proposes a plan and waits for "Build this plan", **Chat** answers and discusses without changing files. Plan and Chat give the agent read-only tools (plus the organization data tools).
- **Access**: previews and published apps sit behind Traefik forward auth, so only signed-in team members can open them, and each app's sharing settings decide who may view or edit it. With single sign-on on, only the organization's people can sign in at all.
